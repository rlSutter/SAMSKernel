## 1.37.1 (8 November 2026; the owner's report from js99er)

- **The disk browser (and the workbench's catalog command) showed nothing with js99er's Myarc floppy controller, and worked with its Generic one.** The browser opened the catalog with record length 0 ("the DSR's own"; the Myarc HFDC refuses 38, which is why it was 0) and **ignored an error on the first read**, so a controller that refuses length 0, or opens it and answers nothing, left a blank list with no message. Now: the frame and `Reading the catalog ...` are drawn **first** (a slow controller, or none, is seen to be being asked); the catalog is opened with length 0 and, if that is refused or the first read fails or comes back empty, **again with 38** (the workbench's `C` does the same); and a failure **shows its error number** (`The disk could not be read: error n`) instead of nothing. **Keys 1-9 choose the drive** (the title says `DSK3.`, the viewer follows), because a Myarc setup in js99er has put the owner's disk on another drive before. Simulator: new options `catalog_lengths` and `catalog_len0_empty` on the stand-in drive (a controller that wants 38 given; one that opens at 0 and reads nothing); group `browser` is 13 checks now (the two kinds of controller, one that refuses the catalog and the message with error 2, the drive keys, and the workbench's `C` on a controller that wants 38). The real DDCC-1, CorComp and TI ROMs already gave the catalog in the simulator at both lengths: **it is js99er's Myarc emulation that answers differently**. **Confirmed fixed by the owner (9 November 2026, js99er with its Myarc floppy controller, a disk in DSK1): the catalog is listed, and opening a file from it works.** Which of the two causes it was (the open at length 0 refused, or its first read empty) is not known: either is now answered by the second try with 38.

## 1.37.0 (8 November 2026)

Prompted by two documents the owner supplied: the Tekumel 4M SAMS schematic (TEK-024) and the proposal for an FPGA replacement machine.

- **The loader finds the SAMS card by what it does, not by reading a register back.** `AMSDET` (write a probe, read it back) is gone: the 4M board's 74LS612 has no path that returns a register to the bus (D0 and D1 grounded, D2 and D3 to the latch's outputs) and the proposal says real cards "do not reliably allow" readback, so a good card could have been refused on real hardware (and an empty bus that remembers the last write could have been accepted). Now `AMSINI` writes the identity map (writes only) and **`AMSSIZ` starts at a distance of 1 page**: if pages `>10` and `>11` are one memory there is **no mapper** (it returns 0; the loader refuses, as before for no card), else it doubles the distance as before. A 16-page card is refused as too small (it aliased at 32 before: "32 pages", also refused). `START`'s order is now: clear the scratchpad variables, identity map, size, refuse if 0 or under `PGMIN`.
- **What the schematic confirmed** (HARDWARE.md, "The SAMS register"): the register layout (even byte = page bits 0-7, the odd byte's low bits = bits 8 and up; a word, odd byte first), the CRU bits at `>1E00`, the 10-bit page of the 4M board (1,024 pages; bits above are ignored), the need to clear both CRU bits on exit (QUIT does not RESET; the kernel's exit already does). `MAPPG` (`SWPB` and a word write) and the identity map (odd byte 0) were right. Nothing else in the kernel writes a register.
- **The simulator has the 74LS612 card** (`tools/sim9900.py`: `ams_latch_model`, `ams_pagebits`, `ams_latch_bits`, `ams_readback`): the low 8 bits from the byte on the bus, the upper bits from a latch that follows every odd-address write on the expansion bus, a word written odd byte first, bits beyond the card's ignored, registers that read `>FF`; and it records any register write that is not the odd byte then the even byte of a word (`ams_violations`). Test group `sams4m` (11 checks): the kernel boots on cards of 512K, 1M, 2M, 4M, 8M and 16M with no readback, and the workbench through a module switch, with no violation; a 16-page card and no card are refused; the model's own semantics (a swapped word gives the page; the page in both bytes gives `n + 256 x (n AND 3)` on a 4M card; a byte alone takes the latch's stale bits). **Two deliberate faults were caught** (a register written as a byte alone, and the page in both bytes).
- **Not verified**: that the pass-through mode (mapping off) shows page n in window n on every card (the identity map relies on it); the latch's polarity (read from the drawing's symbols, consistent with js99er's model, with the kernel's long use on cards of 1M or less, and with the proposal's own statement that a 16-bit access is odd byte first). Checklist steps H1-H4 are for a real 4M or larger card.
- **For the FPGA proposal** (`FPGA-SAMS-NOTES.md`, with the outputs): its 3.4.1 describes the 16M register layout the other way round (the low byte giving bits 0-7) and recommends writing the page in both bytes; both would break this kernel and the schematic's board. Also its speed rule (Stock speed while any CRU bit 0 is set in `>1000->1F00`) catches SAMS at `>1E00`, whose bit 0 the kernel sets and clears on every page switch.

## 1.35.1 (7 November 2026; the owner's report from js99er)

- **Bug fix: quitting from a disk-started program left the F18A in 30-row mode, and the console's title came up wrong.** The owner ran `Hello` from the workbench cartridge's RUN PROGRAM FILE (a disk-started kernel program), pressed FCTN = (Alt = in js99er) and the title screen had garbage on its bottom row. The title is 24 rows; with VR49's 30-row bit still on the F18A also shows rows 24 to 29, which read the video memory after the screen: the console's colour table (`>0380`, row 28) drawn as characters. **Cause**: the kernel's exit (`KEXIT`) puts every F18A register back as at power-up, but only `IF` the F18A flag (`F18FLG`, `>8348`) is set; the disk-start path of the loader (`DISKBOOT`) clears `>8348-837F` and slot A after reading the banks, **and with them the F18A flag** (the comment said F18VER, NPAGES and QUITF stay; F18FLG is at HOT+8, which is in the cleared range, and so is VDPPIC), so the restore was skipped. A cartridge's kernel and a module program were not affected (their loader does not clear it). **Fix**: the loader detects the F18A again after the clears (`BL @F18DET`, four bytes, in the `DISKBOOT` variant only). **Test**: group `diskboot` runs the disk-started Hello in the simulator and now checks that the flag is set while it runs and that FCTN = puts VR10, VR11, VR19, VR24-31, VR49, VR50, VR51 and VR48 back before the console's reset (both checks fail without the fix; the unfixed loader left VR49 = 64, VR29 = 128, VR50 = 2, VR51 = 0). Affected: only the disk-started images (`hello-diskstart-*.dsk`, `workbench-diskstart-360k.dsk`, `prun-test-sssd.dsk`, and `PRUN`'s target); every cartridge is byte for byte what 1.35.0 built. Checklist step D7.
- **Not fixed, and cannot be by the kernel**: a program that sets the F18A's modes itself and is quit by the console's own FCTN = handler (RUN PROGRAM FILE running a third-party program) leaves them as it set them, because no kernel code runs; such a program has to put the registers back (the list is in `OFFREG`, `kernel/f18a.a99`).

## 1.35.0 (7 November 2026)

Second of the owner's accepted list. **No kernel change**: every cartridge built without the new includes is byte for byte what 1.34.0 built.

- **`lib/scroll.a99`: a scrolling tile map on the F18A's second tile layer** (`SCRINI`, `SCRTO`, `SCRBY`; about 1,100 bytes). The map is bytes in memory; the layer is a ring of 64 x 24, 32 x 48 or 64 x 48 tiles (the F18A's two-page name tables); the library writes the tiles that come into view and follows the window with VR10 (the base swaps pages as the window crosses one), VR25 and VR26. - **Not seen on a real F18A**: the page swapping and the two-page rings follow the renderer's model, which restates js99er's F18A; the checklist's S1-S3 are what to look at (the seams at X = 256 and 512, Y = 192 and 384).

## 1.34.0 (6 November 2026)

First of the owner's accepted list (after the questions about scrolling, pixel collision, an object loader and floating point). **No kernel change at all**: two optional includes, so every cartridge built without them is byte for byte what 1.33.0 built.

- **`lib/fixed.a99`: 8.8 fixed-point arithmetic**, about 550 bytes (195 of them tables). `FXMUL`, `FXDIV` (saturating, rounding toward zero), `FXSIN` and `FXCOS` (a quarter-wave table of 65 words), `FXPOL` (an angle and a speed into the Y and X velocities `SPMVEL` takes), `FXATN2` (a direction, within one unit of 256 to the turn), `FXSQRT` and `ISQRT` (exact integer square roots). Angles are a byte, 256 to a turn, 0 east, 64 south. - **`lib/spmpix.a99`: `SPMPIX`, pixel-exact overlap of two sprites**, about 330 bytes, for programs with `"motion": true`. It reads the pattern numbers and patterns from the video memory, so it tests what the chip draws; 8 x 8 and 16 x 16; the corner test first, so far-apart sprites cost no reads; the field wraps at 256 as the motion table does. Not handled: magnified sprites, the F18A's extra sprite planes. Test group `pixel` (5 checks: 520 random pairs against a Python model with about half touching, 14 directed cases, a sprite not in the table, the registers kept; a deliberate fault in the shift direction was caught by it).
- **`examples/aim`** (`aim8.bin`): a turret that aims at a drifting ring with `FXATN2` and `FXPOL`, fires every 64 frames, and counts the hits `SPMPIX` finds (a bullet through the ring's hollow centre is a miss); checked in the `pixel` group (9 shots and 1 hit in 600 frames in the simulator, the ring inside its box, the counts on screen).

## 1.33.0 (6 November 2026)

- **Sprite motion helpers: bounce and collision** (`"motion_helpers": true`, with `"motion"`; the owner's request). **`SPMBOX`** (a range of sprites, the address of a 4-word box in the program's RAM: Y min, Y max, X min, X max in dots): after each step a sprite past an edge **and still going out** is put back as far inside as it was outside and its velocity on that axis negated; one going in is left alone (a sprite placed outside cannot stick); the box is read from RAM every frame (walls may move); sprites outside the range keep wrapping. **`SPMHIT`** (two sprites, their size in dots; R0 = 1 or 0): both Y and X less than that far apart, the screen's wrap taken into account (252 and 3 are 7 apart); a sprite the table does not hold gives 0. **`SPMSWP`** exchanges two sprites' velocities (a head-on meeting of equal balls). **A separate opt-in: +320 bytes** (7,444 with `"motion"`'s 226; the default kernel is still 6,898): a kernel with `"sfx"` (512) cannot also carry the helpers (the free room under the page-pool bitmap is 782 bytes), which is why they are not part of `"motion"`. ## 1.32.1 (6 November 2026; the owner's tests of RUN PROGRAM FILE and the module-program demo)

- **The RUN PROGRAM FILE prompt reads keys properly.** Reported: keys read sporadically, backspace deleting the whole name, no blinking cursor. The cause was a keyboard wait written for a simulator: any scan that saw no key counted as "released" and any scan that saw one as a new press, with no allowance for **contact bounce**, so on a real keyboard one press gave several characters (a bounce on FCTN S several deletions) and keys typed while another was still down were lost. Now (`RNGET`): a key is **new** when its code differs from the last one taken, even if another is still held (so overlapping typing works); it must be **steady for about 15 ms** to count; a key counts as **released** only after it has been up for that long (bounce on release gives no second character); a key already down when the prompt opens (the one that started it) is ignored until released; a held key gives **one character, no repeat**. The **cursor is a solid 8 x 8 block** (character 31, its pattern written by the runner at `>08F8`, as the Editor/Assembler's module cursor is), blinking about every 0.4 s: the underscore of 1.31.1 was drawn but may well have been invisible or too faint. Test group `ea5run` (14 checks) reads the cursor as the block in VRAM and still passes; the contact bounce itself cannot be shown in the simulator, whose keys do not bounce. **To be confirmed on the real machine** (checklist R1).
- **The demo module program does something visible**: a frame counter that ticks every frame (kernel variable `FRAME`, `HEX4`), a count of the keys typed (`DECW`) and the keys echoed, FCTN = quits (the earlier demo was the hello program under another name, which echoes keys but looked like "a screen"). `images/modprog-demo.dsk` has it (530 bytes).

## 1.32.0 (5 November 2026)

- **Module programs: a kernel module on a disk, run by a cartridge that already holds the kernel** (docs/MODPROG.md; the roadmap's "module-only disk programs"). A cartridge built with `"modprog": true` (implies `"ea5"`; the workbench cartridge has it) takes, through RUN PROGRAM FILE, a file that holds one module: **134 bytes plus the module**, against the 4.3K bootstrap and 6.9K kernel of a full disk program. `tools/skmodprog.py guest.a99 --target build/workbench [--disk ...]` assembles the module against the host's `kernel.equ` and writes the PROGRAM file: an option 5 image for `>2000` with a 96-byte stub (what the Editor/Assembler's own option 5 would run: it says `NEEDS THE SAMS KERNEL CARTRIDGE` and returns), a 32-byte header (`SKMP`, version, the host's **kernel build ID**, the module's length, the title) and the module. The **build ID** is the CRC-32 of the host's `kernel.equ` (every exported address and equate), printed by the build (`kernel build ID E8A7222C`) and written to `modid.a99` for the loader; a program for another build is refused with both IDs on the screen. RUN PROGRAM FILE looks at a loaded file before copying it: a single file for `>2000` with the signature after the stub is a module program; it leaves a hand-off in the scratchpad (`>8320` = `>A55C`, the module's VRAM address, its length) and jumps to the loader's start; the loader (`MODPRG`) copies the module over the boot module's page pair after its machine checks and bank copy, and the kernel starts it as the application. The host's other modules, data pages and music stay in place and are reachable through `kernel.equ`. `MODMAX` (8,192, or 4,096 with common code at `>D000`) is in the host's `appcfg.a99` and `kernel.equ`. New files: `kernel/modstub.a99`, `tools/skmodprog.py`, `examples/modprog/guest.a99`; releases ship `images/workbench.kernel.equ` (to build against) and `images/modprog-demo.dsk`. The kernel is unchanged (6,898 bytes); the workbench cartridge's loader bank grows to 4,068 bytes.
- **Sprite motion** (`"motion": true`; `kernel/motion.a99`; the owner's request after asking whether the kernel had it: it had sprites but no motion, the console's auto-motion being switched off). A **motion table** in the program's RAM, 8 bytes a sprite (Y and X as 8.8 fixed point whose high bytes are the attribute table's own, then the Y and X velocities as signed 8.8 dots a frame); `SPMINI` (table, count 0-32, attribute table address: clears the table and starts the motion, a count of 0 stops it), `SPMPUT` (place a sprite and write its entry) and `SPMVEL` (set its velocity). The kernel's step runs once a frame from `KFRAME` (the main loop, `KIDLE`, `KWAIT`: sprites move through a `LINEIN`, a file call or a polling computation), moves every sprite whose velocity is not zero and writes its Y and X bytes to the attribute table; stationary sprites' entries are left alone; positions wrap at 256; the step is skipped inside `KPFR` (which is called mid-stream to VRAM; `SPMSKP`). **Opt-in: +226 bytes** (7,124; the default kernel is still 6,898); four words of slot A (`>20BA`, `>20BC`, `>20BE`, `>20E6`). `examples/motion` is eight bouncing balls. Test group `motion` (12 checks, simulator): positions move by exactly the velocity for each frame (60 steps in 60 frames), the attribute table holds the high bytes, a stationary sprite is untouched, X wraps, the skip flag and a count of 0 stop the step, the build refuses `SPMINI` without the flag, the example's balls stay inside the screen. **Not seen on a real F18A.**
- Test group `modprog` (11 checks): the file's layout and ID; a different kernel build gives a different ID; GUEST boots under the host's kernel and its screen replaces the host's; the hand-off is used once; a program for another build is refused with both IDs and nothing runs; a damaged file is refused; an ordinary option 5 image still runs on the same cartridge; the stub says what is missing where there is no kernel cartridge; the tool refuses a 9,000-byte module and a host built without `"modprog"`. **Not run on real hardware** (checklist M1-M3).

## 1.30.0 (4 November 2026)

- **Found with the TMS9900 cheat sheet the owner supplied (by Stefan Bauch with Lee Stewart, AtariAge): `XOR` was missing from the workbench manual's instruction list** (the native assembler has always supported it); the cheat sheet also agrees with this tree on the five instructions not to execute (`CKON CKOF LREX RSET IDLE`), the jump range and the cycle counts. And **Editor/Assembler option 5 findings** (docs/ROADMAP.md): the module is a GROM, an image cannot rely on its utilities, a program starts at its first load address: the "utilities are the main risk" worry in my earlier notes does not stand.
- **Sound effects: `SFXPLAY` and `SFXSTOP`** (`"sfx": true`, 512 bytes of kernel; TXA's request 2.7 and the owner's "SFXPLAY"). An effect is a short SKM stream (a data entry without `"loop"`, made from a `.txm`, `.mml` or MIDI file) played once beside the song; it **borrows the channels it writes to**: the song's writes to them go to the player's shadow of the chip and not to the chip until the effect ends, is stopped, or is replaced, and then each channel is given the song's last bytes back (silent if no song or the song is paused). One effect at a time; `MUPAUSE` under an effect silences only the song's own channels. The player's variables are five words at `>20F6-20FF`; with the flag off the kernel is unchanged (6,898 bytes). Test group `sfx` (12 checks): a looping song and an effect on voice B and the noise, compared with the song alone frame by frame (they differ only on channels 1 and 3 and only while the effect plays; its own bytes are what the chip is given there; the song's writes held back; afterwards the chip is exactly the song's, for the 680 frames that follow; the same after `SFXSTOP` and after a replacement), an effect with no song ends silent, bad pages answer 1, `MUPAUSE` leaves the effect sounding, and the build refuses `SFXPLAY` without the flag and the flag without the music player.
- **Pictures: `tools/skpic.py`, `lib/picture.a99`** (TXA's requests 1.4, 1.5 and 2.6). `skpic.py` makes a picture record from a PNG (4 colours or fewer: format 2, 256 pixels wide; otherwise format 4, 16 colours in fat pixels) or a TI Artist picture (`NAME_P` and `NAME_C`, cropped or squeezed as TXA does); the build makes one for a data entry whose file ends `.skp` (`"rows"`, default 88, up to 96). `PICSHOW` decodes the pixels into VRAM (run-length decoded straight from SAMS), loads the palette into F18A entries 32-, sets VR31-VR36 and turns the bitmap layer on; `BMLOFF` and `BMLON` switch it. **88 rows because a row is 64 bytes and `>2000-35FF`, the free VRAM in Text 80 with no enhanced colour tiles and no sprite patterns, is 5,632 bytes**; TXA's 96 rows would reach into the file service's buffers. ## 1.4.0 (29 October 2026)

The kernel uses the whole of a big SAMS card: pages are numbers 0-4095 (up to 16M), where they were 0-255 (1M).

- **A clean break in the slot-B save-and-restore idiom.** `CURPA/CURPB/CURPC` (one packed word a slot) are gone; the pager records one page a window in `CURA2 CURA3 CURBE CURBF CURCC CURCD` (`>21E0-21EB`). `GETPB` (new) returns the pages in `>E000` and
  `>F000` in R0 and R1; `SETPB` now takes them in R0 and R1 (it took one packed word in R0). Code that did `MOV @CURPB,R0 ... BL @SETPB` becomes `BL @GETPB` ... `BL @SETPB` with both registers saved. The kernel, the music player and the diagnostic are converted.
- `MAPPG` writes a page with its bytes swapped (`SWPB`), the layout of a 12-bit register; for pages under 256 this is what 1.3.1 wrote. `AMSSIZ` tells 32 ... 4,096 pages (it stopped at 256); `AMSTST` tests them all (about 0.25 million instructions on 16M); the refusal screen shows 3 digits.
- The page pool's bitmap is 512 bytes at `>BE00` in the kernel's own pages (it was 32 bytes in slot A); `skbuild.py` refuses a kernel over 7,680 bytes (it is about 5,000). `"min_pages"` may be 32 ... 4096.
- The self-test checks pages above 255 (each its own page, page >30 undisturbed) and the pool's last four pages. Test group `sams16`: cards of 128K, 1M, 2M and 16M in the simulator, QUIT included.
- Not tried on a real card above 1M, nor in js99er's 16M setting.

## 1.3.1 (29 October 2026)

- **Fix: QUIT on a SAMS of more than 1M.** The page registers were written with the page in both bytes of the word; on a 12-bit card the odd byte is bits 8-11, so identity-mapped page *p* was not page *p*, and switching the mapping off at quit moved the
  kernel's own code out from under it (found by running the 1.3.0 images on a 16M card in js99er: everything worked until QUIT). `MAPPG` and `AMSINI` now write the page in the high byte only. The simulator models 12-bit registers (`tests/test_kernel.py sams16`).
- **Fix: the workbench disk.** It held `MUSIC/A99`, which needs `PD_TUNE` and `PD_SCALE` (data pages of the music app's own build): two undefined symbols on the workbench. The disk now holds hello, `beep` (a new program for the workbench), modes and a probe source, and the test group `nativedisk` checks that all of them assemble and that beep plays its note.
